Five-agent system architecture
Each agent is a specialized role. They share a task queue and write to the same Postgres DB. You orchestrate via a coordinator agent that routes work and handles failures.
A1
Discovery agent — finds and seeds entity stubs
Tools: web_search, fetch_url · Sources: CSR portal company list, NGO Darpan bulk export, MCA CIN database, myScheme API · Output: stub records with name + source URL, queued for enrichment · Rate: ~200 stubs/hour
A2
Enrichment agent — deep-fills each stub
Tools: fetch_url, pdf_reader, structured_extract · Per entity: fetch annual report, CSR chapter, foundation page, BRSR filing → extract sector focus, geography, grant band, eligibility, registrations · Output: field-complete records with confidence tags · Rate: ~30–50 entities/hour
A3
Verification agent — cross-checks and confidence-scores
Tools: web_search, fetch_url · Takes enriched record → searches for contradicting information → compares against 2 independent sources → flags conflicts → assigns high/medium/low confidence per field · Rate: ~60 entities/hour
A4
Drift seeding agent — builds historical baseline
Tools: fetch_url (Wayback Machine), pdf_reader, web_search (prior year filings) · For each verified entity: fetch last 3–4 years of annual reports → extract sector allocations per FY → compute initial drift vectors · Output: change_history rows + initial drift_scores · Rate: ~15–20 entities/hour (slower, multi-doc)
A5
Coordinator / exception agent — routes, retries, escalates
Monitors task queue · Retries failed fetches with alternate sources · Escalates to human review queue when confidence stays low after 3 attempts · Runs daily refresh job for top-50 entities · Generates weekly QA summary report
Data flow: stub → verified record
1
A1 writes stub: {name, source_url, status: "stub"} to DB
2
A2 picks up stubs from queue → fetches all source documents → extracts structured fields → writes status: "enriched"
3
A3 verifies enriched records → resolves conflicts → marks fields with confidence level → writes status: "verified"
4
A4 seeds historical drift data → writes change_history rows → computes initial drift_scores → marks status: "complete"
5
Records with any low-confidence fields go to human_review_queue — your ~4hrs/week is spent here
Parallelism strategy
Don't run one agent sequentially through all 200 companies. Run entity-level workers in parallel batches:
→
Discovery runs once to seed all stubs (few hours)
→
Enrichment runs 10–20 parallel workers, each handling one entity at a time
→
Verification runs immediately after enrichment completes per entity (pipeline, not batch)
→
Drift seeding runs for top-50 priority entities first (most data-rich), then expands
→
Total wall-clock time for 200 entities: ~3–5 days at 10x parallelism
Tool stack per agent
These are the concrete tool calls each agent makes. Design your agent framework so each tool is a typed, retryable function with structured JSON output.
web_search(query)Find company CSR reports, foundation pages, annual reports. Queries: "[Company] CSR report FY2024 filetype:pdf", "[Company] Foundation grant eligibility"
fetch_url(url)Retrieve full page content. Used for CSR portal profiles, BRSR filings, foundation pages, NGO Darpan records
fetch_pdf(url)Download + parse annual report PDFs. Navigate to CSR chapter by section heading. Extract tables of Schedule VII spend.
extract_structured(text, schema)Pass raw document text + target JSON schema → LLM extracts fields with confidence flags. Core enrichment primitive.
db_write(entity, fields)Upsert record to Postgres. Writes field-level source_url + confidence + extracted_at timestamp alongside value.
db_read(query)Read current state of an entity for verification comparison and drift calculation
queue_push(task)Add task to enrichment or review queue. Task types: enrich_entity, verify_entity, seed_drift, human_review
wayback_fetch(url, year)Fetch archived version of a foundation/company page for a given year. Used by drift seeding agent for historical requirement capture.
confidence_score(field, sources[])Compare values across multiple source extractions → return agreed value + confidence level. Flags conflicts for human review.
drift_compute(entity_id)Read change_history rows for entity → compute sector/geo/requirement/openness drift vectors → write drift_scores

Enrichment agent system prompt (core template)
You are a CSR intelligence extraction agent. You will be given a company name, its CSR annual report or foundation page content, and a structured extraction schema. Your job is to extract fields accurately and conservatively. Rules: - Extract only what is explicitly stated. Do not infer or guess. - If a field is not found in the source, set it to null and flag it in missing_fields. - For sector_focus: use canonical taxonomy [Education, Health, Environment, Livelihoods, Women Empowerment, Rural Development, Skilling, Nutrition, Water & Sanitation, Arts & Culture, Sports, Digital Inclusion, Disaster Relief]. - For geography_focus: use state names. If pan-India is stated, include "Pan-India" as a value. - For accepts_proposals: only mark true if source explicitly invites NGO proposals. Default to false if ambiguous. - For confidence: "high" = field explicitly stated with a number or named value. "medium" = implied or described qualitatively. "low" = inferred from context. - Always include the source_url and page/section you extracted from. - Return ONLY valid JSON matching the schema. No preamble.
Verification agent prompt design
You are a CSR data verification agent. You will receive: 1. An enriched company record (JSON) extracted from Source A 2. A second source document for the same company (Source B) Your job: - Compare each field between the record and Source B - For each field: mark as CONFIRMED (sources agree), CONFLICT (sources disagree — state both values), or UNVERIFIED (field not found in Source B) - Upgrade confidence to "high" if both sources agree on an explicit value - Downgrade to "low" and flag for human review if sources materially conflict - Note: minor wording differences are not conflicts. Material conflicts are: different states listed, different spend amounts (>10% variance), contradictory proposal acceptance status. Return: updated record JSON + conflict_log[] + human_review_required (bool)
Drift seeding agent prompt design
You are a CSR drift analysis agent. You will be given annual report CSR chapter excerpts for a single company across multiple financial years (e.g., FY2020, FY2021, FY2022, FY2023, FY2024). For each year, extract: - sector_allocations: {sector_name: spend_cr or spend_pct} — use best available (absolute or relative) - geography_focus: state list - accepts_proposals: bool - key_requirement_changes: any new or dropped eligibility requirements stated Then compute: - sector_drift_signal: which sectors grew, shrunk, or disappeared across years - geo_drift_signal: which states were added or removed - openness_drift_signal: any change in proposal acceptance posture Output one change_history record per year per changed field, plus a drift_summary object. Flag any year where source data was unavailable or ambiguous.
Exception handling: what to do when sources fail
1
Annual report PDF not publicly available → try company investor relations page → try BSE/NSE filing portal → flag as "source_unavailable"
2
Foundation page has no eligibility information → search for past grant announcements → search for CSR committee minutes → mark fields as low confidence
3
Conflicting sector focus across sources → do not pick one — store both in conflict_log → route to human review → human makes final call with source citation
4
Company not on CSR portal → check if obligation threshold met (net profit > ₹5Cr) → if yes, mark as "disclosure_missing" — flag for regulatory non-compliance note
Known agent failure modes — and mitigations
Hallucination of missing fields
Agent invents a plausible but false sector focus or grant amount when source is ambiguous. Mitigation: prompt explicitly bans inference. Verification agent catches this by checking Source B. Confidence scoring exposes low-reliability fields.
PDF extraction errors
Table data in PDFs often misaligns, especially multi-column Schedule VII tables. Mitigation: validate extracted spend figures against CSR portal totals. Flag if variance >10%. Route to human for manual table check.
Stale source pages
Foundation websites often not updated for months after a policy change. Mitigation: always prefer dated documents (annual reports) over undated web pages. Store page hash + fetch date to detect staleness.
Entity resolution errors
"Tata Consultancy Services" vs "TCS Foundation" vs "Tata Trusts" are distinct entities that share parent branding. Mitigation: use CIN from MCA as canonical ID. Never merge entities without explicit human confirmation.
Rate limiting / access blocks
CSR portal and some foundation pages may throttle automated fetches. Mitigation: add delays between fetches, randomize user agents, queue retries with exponential backoff. Keep a whitelist of known-blocked URLs for manual download.
Human review queue: what triggers it
Confidence triggerAny entity with >3 fields marked low confidence after verification pass → human reviews source docs manually
Conflict triggerSources disagree on accepts_proposals, sector_focus (different sets), or spend (>10% variance) → human adjudicates
Missing source triggerNo annual report or foundation page found → human locates source or marks entity as "insufficient data"
Drift anomaly triggerDrift score >80 on any dimension in a single year → possible data error vs genuine shift → human validates before alert fires
New entity triggerFirst-time ingestion of any P1/P2 priority entity → human spot-checks before record goes live
